# Bug Fixer — Bug 修复

## 职责

系统化调试和最小修复。核心原则是 **先找出根因，再尝试修复**。禁止看到报错就猜测性修改。

```
不找出根本原因就不允许修复
```

未完成证据收集和最小复现，不能进入修复阶段。

## 触发场景

- 用户报告 Bug 或异常行为（"报错""不 work""有 Bug""帮我修一下"）
- 测试失败
- 编译/构建失败
- 性能问题
- code-review 指出必须修复的问题

## 工作流程

### 阶段 1：收集证据

收集并记录：

```
□ 完整错误信息、堆栈、行号、错误码
□ 失败命令或操作步骤
□ 输入数据、配置、环境信息（OS、版本等）
□ 当前分支、相关 diff、最近修改文件、新依赖或配置变更
□ 是否稳定复现（每次发生还是偶发）
```

### 阶段 2：建立最小复现

将证据转成最小复现：

- 编译失败：记录最小构建命令。
- 单元失败：保留最小失败测试。
- UI 失败：记录最短操作路径和截图。
- 运行时失败：记录最小输入和触发条件。

**必须确认当前代码上复现失败**（证明 Bug 存在）。这是后续"修复有效"的客观验证标准——复现通过 = Bug 修好了。

### 阶段 3：分析根因

确定根因类型（决定就地修还是回退前置 Skill）：

| 根因类型 | 定义 | 后续 |
|---------|------|------|
| 编码失误 | 需求和设计明确，实现写错 | 最小修复 |
| 编译失败 | 语法、类型、链接、依赖、构建配置错误 | 最小修复 |
| 边界遗漏 | 极端输入、异常状态、并发、资源释放未处理 | 最小修复 |
| UI 契约遗漏 | 设计规范/界面未覆盖必要状态或交互 | 回 `design-brief-builder` 或 `design-maker` 补充后再修 |
| 设计遗漏 | 技术设计/ADR 未覆盖接口、数据、错误处理或兼容策略 | 回 `tech-architect` 补充后再修 |
| 影响面遗漏 | 实际影响超出 tech-architect 判断 | 回 `tech-architect` 重新评估 |
| 需求遗漏 | 验收标准或业务规则缺失 | 回 `product-spec-builder` |

> 需求、设计、UI 或影响面缺失导致的问题，必须回退到对应前置 Skill 补充，不得作为普通编码缺陷直接修复。

### 阶段 4：最小修复

修复原则：

- 只修复当前根因。
- 不扩大需求范围。
- 不做无关重构。
- 不绕过测试。
- 不屏蔽错误来制造通过。

修复后立即运行阶段 2 的最小复现，确认通过。

### 阶段 5：复测和路由

修复后（PM 无独立 code-tester，复测由本技能承担）：

1. 最小复现必须通过。
2. 相关验收场景必须通过。
3. 受影响范围做必要回归。

满足任一条件，重新触发 `code-review`：

- 修改超过局部小修。
- 涉及接口、数据结构、配置、权限或 UI 契约。
- 修改了多个模块。
- code-review 原本要求修复。

```markdown
# Bug 修复报告

已修复 / 待补充设计 / 待补充需求 / 待复现

## 证据

| 项 | 内容 |
|----|------|
| 失败命令/步骤 | |

## 根因

| 类型 | 说明 | 证据 |
|------|------|------|
| | | |

| 文件 | 修改 | 原因 |
|------|------|------|

## 验证

| 验证项 | 结果 | 证据 |
```

完成后追加 milestone 到 `.claude/progress.json`：「Bug 修复：<摘要>（根因：<类型>）」。

## 自审查

```
□ 是否有稳定复现？
□ 是否找出根因而非猜测？
□ 编译失败是否记录了失败命令和错误日志？
□ 修复是否最小化？是否避免无关重构？
□ 根因为需求/设计/UI/影响面遗漏时，是否回退到对应前置 Skill？
□ 是否完成最小复现 + 回归复测？
□ 是否需要重新 code-review？
```
